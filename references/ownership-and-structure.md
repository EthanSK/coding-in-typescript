# Ownership and structure

## Put the behavior where it belongs

- Choose the narrowest coherent owner by responsibility. A feature owns decisions about its records and permissions. A generic transport, storage adapter, or component supplies generic operations. Pass feature configuration at the call site. Check the final imports, public entry points, provider exports, and any feature-specific branches added to shared code.
- Reuse existing read, write, state-change, and validation paths for recovery, persistence, retry, and replay. Trace the owner, including surrounding setup, health, logging, and cleanup. When work requires extraction, use concrete existing callers and verify the original caller as well as the new one.
- Preserve intentionally public and reusable code even if it has one current caller. Look at contract, intended reuse, and history before moving a declaration or removing an export. Add a required public export through the owning module. Count imports as evidence, not as the ownership rule.
- Keep feature and runtime dependencies pointing in the established direction. If libraries depend on each other, show the full import path and where the contract or behavior could live. Get the owner's decision before implementing an architectural workaround. An intra-module file cycle does not automatically call for an architecture change, but check initialization order if it matters.
- Apply the same coding and design standards to internal tools, admin UI, and deployment scripts. Reuse shared primitives, choose least-privilege credentials, use real data or label fixtures, and keep dev-only capabilities inside their intended environment.

## Files, names, and reuse

- Group files that belong to the same exact concept when the framework and repo structure permit it. Keep the implementation, its spec, closely related utilities, templates, and styles together. Keep generic neighbors separate when they have independent purposes. Avoid nesting a lone file or making an umbrella directory solely to make the listing shorter.
- When moving files, update all real entry points. Inspect imports, exports, config paths, globs, test discovery, dynamic loaders, and documentation. Keep ownership and runtime behavior intact for a move-only change. Preserve original names and locations where they give readers useful search points, in line with the local provenance convention.
- Name identifiers for the role and actual value, such as `accountDocumentReference`. Name coordination according to responsibility: a coordinator claims or tracks a job, while a worker performs its unit of work. Keep logical IDs distinct from filesystem paths, protocol headers, and externally owned identifiers. Follow the project's spelling and case conventions. Camel case is a useful default for new code-owned identifier strings. File paths, header names, and protocol values follow their own contracts. For paired required/optional getters, distinguish the optional one explicitly if that is the local convention. A standalone getter that can miss can keep its ordinary name and document absence.
- Order declarations by relevance to the file's named concept. Keep file-level contracts and independent shared declarations near the top. In a class-oriented service, put implementation helpers and constants inside their owning class, then read the file from the top to check that support code does not hide the core operations.
- Start with the existing pattern and a direct implementation. Prefer composition to another copy of the same facts or workflow. Extract a helper when it names a real responsibility or removes meaningful repetition. Remove wrappers, knobs, caches, and abstractions needed only by other new machinery. Confirm the minimal public interface fits the real callers, including existing callers that share its behavior.
