# Data, APIs, and operations

## Stored data and contracts

- Trace writers, readers, projections, fixtures, validators, and permissions as one change. Keep an explicitly stored ID or kind where the domain owns it. A derived document key can be useful for lookup without taking over the identity contract. Keep derived search indexes, query buckets, and summaries in their intended role. The owner remains authoritative.
- Establish who depends on existing data before choosing a migration. In early development with disposable or manually migrated data, prefer the current schema and a separate deliberate backfill. Avoid standing dual reads/writes, legacy cleanup in request handlers, and temporary fallback branches. When existing users or external contracts depend on older data, agree on migration, rollout ordering, and recovery. Audit all code paths and fixtures before handoff.
- Name absolute instants for the event they represent. When adopting a convention, prefer readable forms such as `dateCreated` and `dateLastUpdated`. Translate externally owned names at the boundary when appropriate. Distinguish instants from durations, offsets, local calendar dates, and media positions. Make the unit or zone explicit where ambiguous. Keep suffixes on durations such as `timeoutMs`. When the project already uses milliseconds for absolute instants, avoid repeating the unit in each field name. Keep established protocol field names intact.

## Query and response shape

- Trace the whole request for facts already loaded by admission, guards, or helpers. Reuse a read when actor, target, scope, and freshness match. Carry necessary internal facts to the next step instead of doing another read or exposing an internal field over HTTP. Count reads for empty, typical, and largest supported cases. Explain any repeated read that protects a real invariant.
- Prefer the smallest query that preserves authorization, ownership, availability, filtering, ordering, and pagination. When the product defines empty optional selection as All, omit the predicate rather than sending an empty inclusion set. Test none, one, and all with other filters and a next page. Preserve explicit empty-result semantics when the caller requires them. Check the emitted combined query against the installed backend's operator, index, and combination limits. Validate the write paths for derived calendar buckets or other projections.
- Apply permission and potentially unbounded result filters before cursor and limit selection, or through a data model that can enforce them correctly. A bounded page alone does not make post-filtering safe for counts or pagination. Presentation may remove a fixed known set only where counts and pagination still work. Get agreement before adding fan-out, denormalization, or a wider query solely to simulate an unsupported filter.
- Derive sort choices, IDs, cursor validators, and comparisons from one preset map or query contract. Store the selected ID and resolve the option when constructing the query or local comparison. Preserve tie-breakers, cursor values, intentional required null markers, and visible row order. Range selection follows the rendered order. Test terminal pages, missing and invalid cursors, and cursor transitions.
- Follow existing wire contracts. Prefer named object fields to positional tuples for owned response rows and new JSON response shapes where that is the API convention. A single needs-based object is often sufficient. Preserve established bytes, streams, no-content responses, and protocols with their own layouts. Keep only fields current callers need. Check the actual object from controller to client, mocks, and empty responses.
- Keep access decisions separate from presentation and reference organization. Permission to organize a known reference need not grant content access. Match primary, bulk, and Undo paths against the current rules. Consider whether the presence of a row, ID, token, count, or cursor reveals information. Agree on actual privacy semantics with the owner before changing them.

## Errors and coordination

- An error message should say what was wrong. Derive a short, concrete message from the failing check, even when converting an old framework error. Preserve the approved status/code and expose only information a caller is entitled to know. If two refusal reasons must be indistinguishable, return the same public status and message. Keep diagnostics internal. Check callers, tests, and any user-facing copy for the changed message.
- Reuse the operation owner for atomic claims, retries, stale recovery, progress, and terminal outcomes. A local promise can share same-process work. It cannot enforce cross-instance exclusion. Distinguish queued, admitted, started, completed, failed, and uncertain outcomes. Verify that retrying cannot repeat side effects the user intended once, and that partial bulk failures remain visible and recoverable by the existing semantics.
- For browser-initiated long work, prefer the project's admission and status mechanism when an HTTP request would outlive its useful deadline. Keep immediate admission checks short. If a route returns `202`, describe what that implementation actually accepted. Completion, charging, and refunds go through their owning operations. Verify the UI consumes observed terminal state and the worker can finish after the initial request closes.
- Before proposing a race fix or changing a busy/disabled guard, trace the competing actions, existing admission or claim, exact conflicting order, and actual user impact. State whether observed or theoretical, how likely, and the cost of the fix. Keep protection that covers a reachable failure. If an existing claim already excludes it, preserve the established write path.
- Restore only the information Undo actually needs through authenticated owner APIs. Keep compensating action scoped to a concrete failure. Verify convergence after partial failures, retries, and late results where those are supported. Avoid receipts, secondary status fields, and extra reconciliation layers solely to eliminate a theoretical narrow race.

## Policy and capacity

- Identify who may write each changed field before changing the schema. Keep authoritative writes and local-state updates on the established path. Generate policy artifacts from their owning templates or types when the project does so. Check both the generated output and real policy behavior. Add indexes for real queries and record a usage example in the repository's supported documentation format. Review automatic indexing for new stored fields that are never queried.
- Prefer an existing worker or service tier that meets measured timeout, memory, CPU, concurrency, and isolation requirements. Include temporary files, retries, and overlapping work in the estimate. Compare cold and warm measurements separately. Changing the browser's wait does not reduce the coordinator's own execution time.
- For media and similar compute-heavy changes, trace uploaded and generated inputs, including callers that bypass shared helpers. Explain likely changes to latency, cache reuse, memory, output quality, and cost before implementing a meaningful trade-off. Measure representative inputs with the executing tool version. Separate per-invocation overhead from work that grows with size, duration, or concurrency.
- On a suddenly failing provider path, compare recent code changes, the provider's incident history, and a small unchanged request before rewriting the working path. After recovery, verify the expected data or output instead of relying on a success status alone.
