# Tests and review

## Tests that exercise the real behavior

- Use the closest existing suite and fixtures. Add a test when requested, required by local instructions, or needed for a specific behavior the current coverage misses. Test through the real caller or control when the contract involves bindings, scheduling, persistence, or integration. Use precise test doubles at external boundaries, with typed fixtures. Keep the code that could regress inside the test.
- For UI changes, trigger the actual event, asynchronous callback, or navigation. Assert visible state and actual submitted or persisted data where relevant. Avoid forced refreshes that hide a missing update notification. Cover affected shared callers and the exact state that regressed.
- For data and async changes, cover partial failure, retry, no-op, and boundary-sized cases that exercise the changed contract. Assert query shape and counts when those are the risk. Check both what must happen and which side effect must stay absent. Use the owning setup instead of opening production state or weakening access for tests.
- For end-to-end tests use the normal app entry point, isolated owned data, established selectors and readiness checks, and deterministic assertions. Avoid fixed sleeps, blind retries, and oversized fixtures. Keep diagnosis of flaky tests tied to a reproducible cause. Isolate paid or production-like runs and honor the project's permissions and budget.

## Verification and handoff

- Use the repository's normal task runner and configured formatter. Format the intended files and inspect the formatter diff. Map every changed source/spec to its owning TypeScript project. Transpilation and a passing suite do not establish a passing typecheck. Run the relevant separate spec, lint, build, and test targets where defined, and check related owners where a shared contract changed. Choose the smallest checks that cover the actual risk.
- Verify the selected tests actually ran, with the intended suite paths and a nonzero count. Read the full failure summary before calling an aggregate run passed. Distinguish a targeted run, full suite, compiler result, lint result, reported IDE diagnostic, and manual check. Confirm an editor warning in the originating project and TypeScript SDK when the task is about the editor.
- For live verification, use the exact environment, build, account, and route affected by the change. Exercise the real workflow with an appropriate fixture. A responding URL does not prove authentication or a working UI. Avoid reusing stale build evidence. Leave an environment available for user review when requested or required, following its lifecycle rules.
- Compare the whole in-scope diff with the intended behavior and its neighboring contracts. For each material finding, establish the trigger, actual result, affected caller or user, and evidence for the proposed change. Distinguish observed from theoretical failure, and known earlier behavior from regression. Give a specific source location. Be especially careful with stored fields, access scope, cross-surface effects, and changes to tuned code.
- Fix small unambiguous in-scope defects only within the authority the review gives you. Report remaining findings and unresolved coverage. Record the rationale for a dismissed finding at the owning code when it explains a durable invariant. Preserve unrelated work, and follow the project's staging and publishing rules.
